# 主群 Agent 与话题会话设计（模仿 Claude Tag）

替代此前“关键词识别”“主群只在 @ 时读有界背景”“明确 @ 才产生回合”的做法。
实施分支：`feat/runner-bridge`。参考资料：Claude Tag 官方文档（how-it-works、when-claude-responds、memory、
create-artifacts、proactivity）与 Slack 帮助中心，链接见文末。

## 1. 用户确认的目标

1. **完全模仿 Claude Tag 的模式**：
   - 群有一个长期的“群会话”（主群 Agent），读取主群全部消息；
   - 每个话题是独立的“工作会话”；
   - 话题内免 @；
   - 偶尔主动说话；
   - 有群记忆；
   - 支持把讨论变成总结与分工。
2. **所有意图由 AI 识别，不用关键词规则**；权限与安全由代码校验。唯一例外是第 7 节的“停止”。
3. **群会话跑在服务器 team-runner 的 Codex 上**：
   - 群讨论不只是总结和分工，也可能需要调研、搜索、读代码；
   - 话题会话仍按已有规则选择机器，未指定时用服务器。
4. **“全部读完”**：
   - 主群消息全部入库，不设“最近 20 条”之类的人为上限；
   - 超出模型窗口时，近期的给原文，更早的压成要点，原始记录可回查。

## 2. 会话模型

```text
飞书群
├─ 主群时间线 ──→ 群会话（每群一个，team-runner 上的持久 Codex thread，工作区只读）
│                  · 读取全部顶层消息、话题进展摘要、群记忆
│                  · 处理顶层 @，判断并执行主动回复
└─ 话题（每个一个）──→ 工作会话（独立工作区与 Codex thread，按话题选择机器）
                   · 话题内所有消息免 @ 接续，任何获准成员可引导
```

与 Claude Tag 对应：

- 顶层 @ 先交给频道会话；
- 能直接答的，在消息下的话题里回答；
- 需要调查、工具或较长往来的，在该话题里启动工作会话，此后话题绑定该会话；
- 两个话题是两个会话，互不共享状态。

## 3. 消息流

| 消息 | 处理 |
|---|---|
| 顶层，@ 机器人 | 交给群会话处理，带上自上次以来的全部新消息。群会话结构化输出以下之一：<br>① `answer`：在该消息下的话题里回答；<br>② `start_task`：在该话题里建立工作会话，附群会话写的背景交接，按需选择机器、执行或讨论；<br>③ `memory`/`settings`：写入群记忆；<br>④ 授权、撤权等管理动作：交给代码按权限执行。 |
| 顶层，未 @ | 入库。未暂停时，由 Bridge 意图模型判断 `none` / `reply` / `handoff`（第 4 节）。 |
| 话题内（有 `threadId`、映射到已有会话） | 免 @ 接续该工作会话。先经 Bridge 意图模型判断是否为控制或管理动作（停止、进度、接受、退回、恢复、插话、协作者、归档、删除、授权）。 |
| 主群对任务消息的“引用回复”（无 `threadId`） | 视为顶层消息。 |

## 4. 主动说话（偶尔）

默认保守，大多数未 @ 消息不回应。只有以下情况才动作：

- **有人明确提出它能直接解决的需求**：在那条消息下的话题里简短回复一次，提出可以帮忙或直接给出答案。
- **它已知答案、一条消息能说清**：在该消息下的话题里简短回复一次。
- **新消息与进行中的任务有关**：不在主群说话，转交给该话题的工作会话：
  - 任务运行中，以插话方式送达；
  - 任务空闲，作为背景加入该话题，并排一个“如无影响可不回复”的回合。模型输出 `NO_REPLY` 时不投递。

判断由 **Bridge 意图模型**完成，追求快速；真正的回答交给 team-runner 上的群会话生成。判断输入包括：

- 最近若干条顶层消息；
- 进行中任务的标题与摘要；
- 群记忆，含主动回复设置。

**开关与自然语言调整**：

- 按群保存 `autoReply: conservative | mention_only`，默认 `conservative`；
- 可用自然语言调整，例如“@机器人 只在被 @ 时回复”“@机器人 没人 @ 也可以回答部署问题”；
- 意图识别为 `settings` / `memory` 后写入群记忆，并回复确认；
- 话题级可说“这个话题别再自动回复了”。

**约 100 条暂停跟读**：

- 自从机器人上次在群里发言或回复后，顶层又累积约 100 条消息、它一直没参与时，暂停逐条调模型判断，只入库；
- 有人 @ 它即恢复，计数清零；
- 作用：控制成本、避免无关闲聊稀释群会话、降低乱插话风险；
- 阈值可配置，默认 100。

## 5. “全部读完”的实现

- **完整入库**：Bridge 已接收群内全部消息（`receiveBackground`）。首次启用群会话时，用机器人身份对群时间线及其话题完整翻页导入历史，标记为导入，不触发任何回合。
- **增量补给**：
  - 群会话保存“已喂到”的游标；
  - 每次 @ 或主动回复生成回答时，把游标之后的新顶层消息和话题进展全部补给；
  - 积压超过预算（默认约 60,000 字符）时，最近部分给原文，更早部分先由 Bridge 意图模型压成要点。
- **可回查原文**：每次群会话回合前，Runner 把该群完整原始记录写入群会话工作区的 `/workspace/.group/history.md`（只读挂载给模型）。群 Agent 需要细节时直接检索。为此 Job 协议新增 `files` 字段，由 Runner 在模型启动前写入。
- **压缩兜底**：
  - Codex 自身会在窗口吃紧时压缩较早内容；
  - 稳定事实（决定、负责人、约定）进入群记忆，不依赖窗口。
- **会话寿命**：群会话的 Codex thread 长期复用。不照搬 Claude Tag“空闲约 1 小时换新”，因为用户要求不丢主群上下文。管理员可用 `!重置群会话` 重建，重建时会重读群记忆和历史文件。

## 6. 群记忆、话题回流、总结与分工

- **群记忆**：
  - 按群保存简短条目，包括约定、负责人、决定、自动回复设置；
  - 三种写入方式：成员说“记住：……”；群会话在结构化输出中自行记录决定；管理员修正；
  - “你记得这个群什么”可以列出；任何获准成员都可以更正或删除；
  - 每次群会话回合和主动回复判断都会读取。
- **话题回流**：每个工作回合结束（完成、失败或停止）时，把一行摘要写回群时间线的内部事件，例如“[话题 X｜负责人｜状态] 结论或改动”。下次补给给群会话。“总结一下我们说的”因此覆盖主群和所有话题。
- **总结与分工**：
  - 群会话输出结构化结果：结论、未决问题、待办（内容、负责人 open_id、截止）；
  - Bridge 渲染为 `<at user_id>`，负责人只能是获准成员；
  - 用户可以接着说“按这个分工开话题”，确认后为每项建立工作会话，负责人为对应成员。

## 7. 意图识别（全部 AI）与唯一例外

**Bridge 意图模型**对每条 @ 消息和话题内消息输出一次结构化 JSON，字段大致为：

```text
kind: chat | task | control | grant | revoke | memory | settings
control: stop | status | accept | reject | recover | steer | allow_collaborator | revoke_collaborator | archive | delete_request | delete_confirm
mode: discuss | execute
machine / own_machine / project
deliver_markdown / read_attachments / attachment_kinds
```

- 删除 `command()`、自然派活正则、`requestsChatContext`、附件与 Markdown 正则、句首机器正则等关键词规则。
- 模型只能从候选中选机器和项目；被授权人与负责人只取实际 @ 的获准成员。
- 执行、授权、验收、删除等都由代码按现有权限交集校验，模型不能扩大权限。
- 意图模型不可用时：不执行任何有副作用的动作，回复“暂时无法理解，请稍后再试”。

**唯一例外“停止”**：

- 任务话题里整条消息恰为 `停止`、`!停止` 或 `!stop` 时，无论是否 @，都不经模型，直接停止该话题当前执行与排队回合；
- 仍需负责人、Leader 或执行协作者身份；容器与子进程确认结束后才回复“已停止”；
- 主群单独“停止”不执行，提示到话题里停止；
- 自然语言“先别做了”由 AI 识别为停止，效果相同；
- 管理命令以 `!` 开头，同样不经模型，例如 `!重置群会话`（仅 Leader）。

## 8. 群会话执行环境

- 在 team-runner（共享服务器节点）上运行，持久 Codex thread 和状态卷，工作区只读；
- 不写业务仓库，需要改代码时一律开话题、建工作会话；
- 联网搜索与调研：优先启用 Codex `tools.web_search`，由 provider 服务端完成搜索，不扩大容器出网。provider 是否支持需实测，见第 10 节；
- 如需抓取网页原文，可为群会话单独配置“仅公网 HTTPS”的出网模式，私网与元数据地址仍阻断。任务工作会话保持原允许列表；
- 结构化输出使用 App Server `turn/start` 的 `outputSchema`。

## 10. 风险与待核实

- provider 对 `web_search` 工具的支持未验证。不支持时，调研只能依赖可访问的公网抓取，需单独评估出网策略。
- 每条未 @ 顶层消息一次意图调用（约 2.5–5 秒、按量计费）。100 条暂停机制兜底，阈值可配置。
- 群历史可能很大：首次导入、`history.md` 写入和压缩都要分页并设置上限告警，不静默截断。
- 主动回复可能打扰成员：默认保守，可按群关闭；话题级“别再自动回复”。
- 本设计改变“明确 @ 才产生回合”的原 Runner 计划，已获用户确认。

实现中确认的几个关键事实（基于 Codex 0.153.4）：

- 自定义 provider 下联网搜索需要同时设置 `web_search = "live"` 与 `model_providers.<id>.supports_standalone_web_search = true`；
- 内置 `update_plan` 工具不可用，清单改由执行回合注册的自定义工具 `update_checklist`（App Server 实验性接口）提供；
- 不在 Codex 内置列表中的模型需要提供模型元数据（`model_catalog_json`），否则上下文与工具能力退回默认值。

## 真实飞书双人验收清单

成员 A（Leader）与成员 B各用自己的飞书账号，在测试群依次完成，每项记录截图和是否符合预期：

1. 主群不 @ 聊 10 条以上关于导入规则的讨论，其中夹 1 条闲聊。机器人不说话、不点表情。
2. A：`@机器人 总结一下我们刚才说的，按讨论分个工`。
   - 提问消息上出现表情；
   - 话题里的回答覆盖讨论要点，分工 @ 到 A、B；
   - 回答不再重复列一遍分工。
3. A：`@机器人 按这个分工开话题`。群里出现每项的【分工】消息；B 在自己的话题里回复“开始，按要求改”，任务执行并回传成果。
4. B 在主群不 @ 问：`feedbackdesk 的测试怎么跑？`。机器人在该消息下的话题里简短回答一次。
5. B 在主群不 @ 补充一条与第 3 步任务相关的细节。主群不出声，对应话题收到转交（运行中为插话，空闲时简短说明或静默）。
6. A：`@机器人 记住：周报一律用表格`，再问 `@机器人 你记得这个群什么`；然后 `@机器人 以后只在被 @ 时回复`，确认第 4 步类问题不再主动回答。
7. 任一执行中的话题里发 `停止`。不 @ 即停，回复“已停止”。
8. `@机器人 查一下 Node.js 最新 LTS 版本`：回答带来源链接。
